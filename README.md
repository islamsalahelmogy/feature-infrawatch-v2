# InfraWatch V2 — خطة التنفيذ

نظام لمراقبة البنية التحتية وأجهزة الشبكة في عدة مواقع ومصانع، وتسجيل الأعطال ومتابعتها وإخطار المسؤولين بنتائج الفحوصات المجدولة.

هذه الوثيقة تفصل الموجود في الكود عن المطلوب تنفيذه. البنود غير المحددة بعلامة إنجاز هي خطة عمل وليست ميزات جاهزة. تحديث الخطة: 8 نوفمبر 2026.

## المتطلبات الجديدة

1. بعد اكتمال كل اختبار مجدول، يرسل النظام بريدًا مجمعًا بالأجهزة المفصولة إلى الـ Administrators.
2. توفير CRUD لإضافة الـ Administrators وعرضهم وتعديلهم وحذفهم، مع التحكم في استقبال التنبيهات.
3. نقل إشعارات البريد من المرحلة السادسة إلى المرحلة الثانية، لتكون جزءًا من أول إصدار مراقبة قابل للاستخدام.

### السلوك المقترح للبريد

- المقصود بالـ Administrator في الخطة هو حساب مستخدم بدور `administrator`؛ نستخدم نظام المستخدمين والصلاحيات الموجود بدل إنشاء حسابات موازية.
- يرسل ملخص واحد لكل مستلم فعّال ومفعّل له استقبال التنبيهات، بعد اكتمال التشغيل وحفظ نتائجه، وليس رسالة مستقلة لكل جهاز.
- يحتوي الملخص على الأجهزة التي أصبحت أو ظلت `down` ضمن نطاق ذلك التشغيل، واسم الجهاز وIP والموقع والأهمية وآخر فحص ناجح ووقت الفشل ورابط التفاصيل.
- يحدد `failure_threshold` متى يصبح الجهاز `down`؛ الفشل قبل بلوغ الحد يظهر `degraded`. عدم استلام نتيجة أو توقف الـ Worker لا يعني أن الجهاز مفصول.
- إذا لم توجد أجهزة مؤكدة `down` فلا يرسل بريد أعطال افتراضيًا. يمكن لاحقًا تفعيل ملخص نجاح منفصل.
- إذا استمر العطل، يظهر الجهاز في بريد التشغيل المجدول التالي أيضًا، تطبيقًا لمتطلب الإرسال بعد كل اختبار. منع التكرار يخص إعادة إرسال نفس التشغيل لنفس المستلم فقط.
- التشغيل اليدوي لا يرسل بريدًا افتراضيًا؛ يمكن إضافة خيار إرسال صريح له.
- التشغيل الجزئي أو المنتهي بمهلة يعرض النتائج المؤكدة فقط مع بيان الأجهزة التي لم تُفحص. إذا لم توجد نتائج Down، يسجل فشل التشغيل ويظهر تنبيه تشغيلي منفصل.
- يضم البريد اسم الجدول ورقم التشغيل ووقت البدء والانتهاء والمنطقة الزمنية وعدد الأجهزة المفحوصة والمفصولة وغير المفحوصة.

هذه التفاصيل افتراضات تصميم قابلة للتعديل؛ المتطلب الأساسي هو إرسال الأجهزة المفصولة بعد الفحص المجدول وإدارة المستلمين.

## Phase 1 — الأساس وإدارة الأجهزة والصلاحيات

**الحالة:** الأساس منفذ، وقبول الإنتاج معلق.

- [x] تسجيل الدخول وحماية الجلسات وتحديد محاولات الدخول.
- [x] الأدوار والصلاحيات الأساسية.
- [x] إدارة المواقع والأجهزة وأنواعها وربطها بملفات المراقبة.
- [x] إعداد interval وtimeout وretries وfailure threshold.
- [x] Dashboard أساسية وعرض نبضات العمال.
- [ ] تجهيز MySQL المستهدفة وتنفيذ migrations وseed والتحقق من دخول المدير.
- [ ] مراجعة بيانات الأجهزة والمواقع ونطاق الأجهزة المسموح بفحصها.

**معيار القبول:** نجاح اختبارات المرحلة، وتجربة CRUD والصلاحيات على البيئة المستهدفة بحسابات الأدوار الثلاثة.

## Phase 2 — الفحص المجدول وإدارة المسؤولين والبريد

**الحالة:** قيد التطوير؛ هذه أولوية الإصدار التشغيلي الأول.

### 2.1 تثبيت محرك المراقبة

- [x] أساس Python Worker وICMP وWorker API وHeartbeats.
- [x] حفظ النتائج وتحديث الحالة وفتح Incident وإغلاقه عند التعافي.
- [ ] تجربة Worker على شبكة فعلية والتحقق من timeout وretries وfailure threshold.
- [ ] حماية استقبال النتائج من التكرار والترتيب المتأخر والتزامن حتى لا تنشأ أعطال مكررة أو تعود حالة قديمة.
- [ ] تحديد حد للتوازي واختبار أثره على الشبكة والأجهزة.

### 2.2 Scheduled Runs

- [ ] إدارة جداول الفحص: الاسم، التوقيت والمنطقة الزمنية، النطاق حسب الموقع أو مجموعة الأجهزة، والتفعيل والتعطيل.
- [ ] فصل جدول التشغيل الذي يحدد موعد ونطاق الجولة عن Monitoring Profile الذي يحدد طريقة الفحص وحدوده؛ منع تشغيل الآليتين لنفس الفحص مرتين.
- [ ] إنشاء Run ID لكل جولة وحفظ قائمة الأجهزة المستهدفة وقت البدء، وعدد النتائج المتوقعة والمستلمة ووقت الانتهاء.
- [ ] حالات تشغيل واضحة: pending / running / completed / partial / failed / cancelled.
- [ ] قفل يمنع التداخل لنفس الجدول، مع سياسة موثقة لتخطي الموعد أو تأجيله إذا كانت الجولة السابقة تعمل.
- [ ] استعادة الحالة بعد إعادة تشغيل العامل، واستخدام deadline وlease لمنع بقاء تشغيل عالق إلى الأبد.
- [ ] عدم اعتبار التشغيل مكتملًا إلا بعد حفظ نتائج جميع أجهزته، أو إنهائه صراحة بحالة جزئية أو فشل.

### 2.3 Administrators CRUD

- [ ] قائمة المسؤولين مع البحث والتصفية وعرض تفاصيل الحساب.
- [ ] إضافة مسؤول بالاسم والبريد الفريد وكلمة مرور محفوظة بطريقة آمنة.
- [ ] تعديل الاسم والبريد وحالة الحساب وإعداد استقبال تنبيهات الفحص.
- [ ] تعطيل وحذف المسؤول مع الاحتفاظ بسجل أحداثه التاريخي؛ استخدام soft delete عند الحاجة.
- [ ] منع حذف أو تعطيل أو تغيير دور آخر Administrator فعّال، ومنع المدير من إزالة صلاحياته عبر هذه الشاشة.
- [ ] قصر إدارة المسؤولين على دور administrator، وتسجيل من أضاف أو عدّل أو حذف الحساب.
- [ ] استبعاد الحسابات المعطلة والمحذوفة وغير المشتركة من الرسائل، وإبطال جلسات الحساب المعطل.

### 2.4 Email Notifications

- [ ] إعداد SMTP واسم المرسل والعنوان، دون إظهار الأسرار في الواجهة أو السجلات.
- [ ] بناء قالب بريد مجمع قابل للقراءة ومتوافق مع تفاصيل السلوك أعلاه.
- [ ] استخدام Queue مستقلة للإرسال بعد حفظ وإغلاق التشغيل؛ فشل البريد لا يلغي نتيجة الفحص.
- [ ] سجل تسليم لكل تشغيل ومستلم: pending / sent / failed، مع المحاولات ووقت الإرسال ورسالة خطأ آمنة.
- [ ] مفتاح فريد `(run_id, recipient_id, notification_type)` لمنع إنشاء وظائف بريد مكررة لنفس الملخص.
- [ ] Retry مع backoff وحد أقصى وإعادة محاولة يدوية مسجلة. لا يمكن ضمان وصول البريد مرة واحدة تمامًا باستخدام SMTP وحده إذا انقطع الاتصال بعد قبول الرسالة؛ يسجل النظام الحالات الملتبسة.
- [ ] إظهار فشل التسليم وعدم وجود مستلمين فعّالين في لوحة الإدارة، مع رسالة اختبار بريد للمدير.

**معيار القبول:** جولة بها أجهزة سليمة وأجهزة تجاوزت حد الفشل تنتهي بملخص صحيح لكل مسؤول مؤهل؛ تكرار طلب إنهاء الجولة لا ينشئ ملخصًا جديدًا؛ استمرار العطل في جولة جديدة ينتج بريدًا جديدًا. تغطي الاختبارات أيضًا غياب المستلمين، فشل SMTP، توقف العامل، النتائج المتأخرة، عدم وجود أعطال، وصلاحيات CRUD وحماية آخر مدير.

## Phase 3 — مراقبة تفصيلية للأجهزة

**تعتمد على:** استقرار جمع النتائج ودورة التشغيل في Phase 2.

- [ ] SNMP للأجهزة المدعومة: الواجهات واستهلاك bandwidth وCPU والذاكرة حسب إمكانيات الجهاز.
- [ ] Windows Monitoring: CPU وRAM والأقراص والخدمات المطلوبة عبر طريقة اتصال معتمدة في البيئة.
- [ ] FortiGate Monitoring: حالة الواجهات وموارد الجهاز والجلسات وحالة الأنفاق حسب ما تدعمه الأجهزة.
- [ ] حفظ وعرض Performance Metrics ورسومها التاريخية؛ وجود جدول metrics الحالي لا يكفي وحده.
- [ ] تشفير بيانات الاتصال، وضبط صلاحياتها، وعدم إرسالها للمتصفح أو تضمينها في البريد.
- [ ] ربط حدود القياسات بالأعطال وإضافة نوع الفحص إلى الملخصات دون خلط تعطل خدمة بفصل الجهاز.

**معيار القبول:** مقارنة قراءات كل Collector بجهاز تجريبي فعلي، واختبار فشل بيانات الدخول وعدم دعم بعض القياسات دون إيقاف بقية الجولة.

## Phase 4 — WAN وVPN وTopology واكتشاف الأجهزة

- [ ] متابعة روابط WAN وأنفاق VPN وقياس latency وpacket loss.
- [ ] Network Discovery لنطاقات معتمدة، مع مراجعة النتائج قبل إضافتها إلى Inventory.
- [ ] خريطة تربط المواقع والروترات والسويتشات والأجهزة، مع تمييز الروابط المؤكدة عن المستنتجة.
- [ ] تعريف Dependencies: الجهاز أو الرابط الذي تعتمد عليه أجهزة أخرى.
- [ ] تجميع الأعطال التابعة لانقطاع رابط رئيسي وتوضيح السبب المحتمل داخل البريد مع إبقاء قائمة الأجهزة المتأثرة.

**معيار القبول:** اكتشاف نطاق تجريبي دون أجهزة مكررة، وعرض انقطاع رابط وعلاقته بالأجهزة التابعة دون تقديم السبب المستنتج كحقيقة مؤكدة.

## Phase 5 — IP وDHCP Intelligence

- [ ] رصد تعارض IP عند توفر أدلة كافية من مصادر الشبكة، وإرفاق مصدر ووقت الملاحظة.
- [ ] متابعة تغير علاقة IP وMAC والتنبيه على جهاز غير معروف.
- [ ] ربط بيانات DHCP المتاحة وعرض leases والاستخدام والسعة المتبقية.
- [ ] مقارنة الواقع بالمخزون المسجل وإتاحة مراجعة الفروق قبل تعديل البيانات.
- [ ] سجل تاريخي لتغيرات العناوين، مع استثناءات للأجهزة والتغييرات المعروفة.

**معيار القبول:** سيناريو تعارض وتغير MAC واستيراد DHCP داخل بيئة تجريبية، دون تعديل الشبكة أو سجلات Inventory تلقائيًا.

## Phase 6 — التقارير والتشغيل والإطلاق

- [ ] تقارير Availability وDowntime وMTTR والأجهزة الأكثر أعطالًا حسب الموقع والفترة، مع تعريف طريقة الحساب واستبعاد البيانات المفقودة والصيانة بشكل صريح.
- [ ] تصدير التقارير وإرسال تقارير دورية؛ بريد الأعطال الأساسي يُنفذ بالفعل ضمن خطة Phase 2.
- [ ] Retention وأرشفة وتنظيف تدريجي للنتائج والقياسات وسجلات البريد مع فهارس مناسبة.
- [ ] تغليف Python Worker كـ Windows Service مع restart تلقائي وسجلات وتشخيص.
- [ ] تشغيل Scheduler وQueue بصورة دائمة ومراقبة صحتهما، وإظهار آخر تشغيل ناجح وآخر تسليم بريد.
- [ ] نسخ احتياطي وتجربة استرجاع فعلية، وإدارة الأسرار وتدوير توكنات العمال.
- [ ] اختبار الحمل بحجم الشبكة المستهدف، ثم Pilot على موقع واحد، ثم التوسع تدريجيًا.
- [ ] دليل تشغيل يشرح التعامل مع Worker متوقف وQueue متراكمة وSMTP غير متاح.

**معيار القبول:** اعتماد نتائج الـ Pilot، ونجاح الاسترجاع والتشغيل بعد restart، وعدم فقد الجولات أو إنشاء إشعارات مكررة عند إعادة المعالجة، وتوثيق حدود الأداء المعتمدة.

## اقتراحات Features إضافية

هذه اقتراحات مبنية على احتياجات النظام، وليست توسعًا معتمدًا للتنفيذ تلقائيًا.

| الأولوية | الميزة | فائدتها | المرحلة المناسبة |
| --- | --- | --- | --- |
| عالية | Maintenance Windows | توضيح أن الجهاز تحت صيانة وتقليل التنبيهات غير المفيدة؛ استثناء البريد يتطلب سياسة معتمدة | بعد 2 |
| عالية | Recovery Email | إبلاغ المسؤول برجوع الجهاز ومدة العطل بدل انتظار فتح Dashboard | بعد 2 |
| عالية | Acknowledge + Assign + Notes | تحديد من يتابع العطل وما تم عمله لتقليل تكرار الجهد | بعد 2 |
| عالية | Monitoring Health | كشف توقف العامل أو الـ Scheduler أو Queue، لأن غياب الفحوصات ليس دليل سلامة | 2 و6 |
| عالية | Site-based Recipients | إرسال أعطال كل موقع إلى المسؤولين عنه، مع مسؤول مركزي يشاهد الكل | بعد 2 |
| متوسطة | Escalation Rules | تصعيد العطل الحرج إذا استمر مدة محددة دون متابعة | بعد إدارة الأعطال |
| متوسطة | Flapping Detection | تمييز الجهاز الذي يفصل ويرجع باستمرار عن عطل مستمر | 3 |
| متوسطة | Device Tags + Bulk Actions | تسهيل إدارة مجموعات كبيرة وتغيير ملفات المراقبة لعدة أجهزة | 3 |
| متوسطة | HTTPS / TCP / DNS Checks | كشف توقف خدمة حتى لو الجهاز يستجيب لـ Ping | 3 |
| متوسطة | SLA Dashboard | إظهار التزام كل موقع أو خدمة بمستوى الإتاحة المطلوب | 6 |

**ترشيحي لأول توسع بعد المتطلبات الأساسية:** Maintenance Windows، ثم Recovery Email، ثم Assign/Acknowledge. هذه الميزات تكمل دورة التعامل مع العطل من اكتشافه حتى عودة الخدمة. لا يغيّر أي تجميع أو تصعيد مقترح شرط البريد بعد كل تشغيل إلا بقرار صريح.
